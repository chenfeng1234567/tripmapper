TripMapper — Write-up

CSE 512 · Assignment 3 · Interactive Visualization

1. The question

Given a trip plan — a list of places spread across days, with travel time and mode between them — how can a traveler quickly see the shape of the trip, and then refine it on the spot?

A spreadsheet of stops is easy to write but hard to read. A static map shows geography but loses the schedule. TripMapper joins both views and adds a small set of interactive techniques so the same data can answer questions like:

  • Which day is the most travel-heavy?
  • Show me only the food stops.
  • What's the quickest route through Day 2 if I reorder it by distance?
  • Move this museum from Day 1 to Day 2 — does the day still fit?
  • What's the address again? Click a marker.

2. Design rationale

Encoding day on the marker, category inside it

A trip is fundamentally a sequence, so the eye should trace day-routes first. We encode the day with the marker's ring color (the same color as the polyline that connects the stops on that day) so the route reads as a single visual unit. Category is shown as a small emoji glyph inside the ring — it answers "what kind of stop is this?" in a glance without competing with the route encoding. A small numbered badge in the corner gives the order within the day.

Two-layer day bars in the overview

For each day we render a small bar split into a solid block (time spent at stops) and a hatched block (time in transit). This surfaces patterns like "Day 3 is mostly driving" without forcing the reader to do mental arithmetic on the schedule.

Travel-time pills sit on the route, not on the markers

The pills with travel time and mode emoji float at the midpoint of each polyline segment. This puts the schedule visually on the route rather than next to a stop, and we made the pills non-interactive so they never block marker clicks.

Sidebar mirrors the map

Filters, sort controls, day chips, and the place list all reflect the same data subset. Selecting a stop in either view updates the other — multi-view coordination without a third "details" pane to keep in sync.

Dynamic queries, brushing, and direct manipulation

We layered three classic interaction techniques from the readings:

  • Dynamic queries. Day filter (single-select) and category filter (multi-toggle) re-render the map and the list immediately, no apply button.
  • Brushing-by-encoding. Selecting one stop dims all other markers so the chosen stop pops out without losing context.
  • Direct manipulation. Stops can be edited, added, deleted, or reordered within a day right from the panel; the map updates synchronously. The trip can be exported back to .xlsx, closing the loop with the user's source data.

Alternatives we considered

  • Marker color = category, line color = day. Tried first; harder to scan because the marker is the more salient mark and category was competing with day for attention. Reversed.
  • Tabs per day with no "all days" view. Cleaner per screen but we lost the cross-day overview. Final design keeps tabs and an "All" mode with day dividers in the list.
  • Drag-and-drop reorder. Nicer than up/down buttons, but pulled in a dependency for marginal gain. Left for the final project.
  • Heatmap of stop density. Considered for "where is this trip clustered?" but redundant with the polylines on a small number of stops. Skipped.
  • An LLM trip generator (the original prototype). Removed because the assignment rewards exploratory interaction on a chosen dataset, not generation quality, and the API dependency conflicted with the static-site deployment requirement.

3. References

  • Map tiles: OpenStreetMap contributors (tile layer + place coordinates).
  • Map library: Leaflet via react-leaflet.
  • Spreadsheet I/O: SheetJS (xlsx) for reading and writing .xlsx files entirely in the browser.
  • UI framework: React + Vite.
  • Visual reference: pitravel.cn — for the side-by-side list-and-map layout and the travel-time pills on the route.
  • Course readings: Ahlberg & Shneiderman 1994 (dynamic queries / brushing); Wattenberg 2005 (NameVoyager) — both shaped how we approached filter responsiveness and incremental exploration.

The Seattle sample data is hand-curated from public information; coordinates are from OpenStreetMap.

  • Keeping the map and list in sync. Re-rendering polylines, travel pills, and selection state correctly whenever a filter changes (without flicker or stale layers) was the trickiest piece of the React/Leaflet integration.
  • Round-tripping Excel. Supporting both upload of arbitrary .xlsx files (with case-insensitive columns, missing fields, validation messages) and export back to .xlsx took longer than expected.
